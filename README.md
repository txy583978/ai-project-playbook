# AI Project Playbook | AI全栈项目开发实战手册

> 版本：v0.4（2026-11-21，annotated tag 已打，已推送 origin/main）｜步骤编号与改动记录见 [CHANGELOG.md](CHANGELOG.md)

一套从需求分析到部署上线的完整AI辅助项目开发模板，配合AI写代码，让你从0到1做出专业级项目。

## 这是什么？

这是一套**教练式AI提示词模板集**，把全栈项目开发拆成 0–10 主线步骤、第11步可选增强、第12步部署，每一步都有专门的模板引导你：
- 该问什么问题
- 该输出什么结果
- 常见错误是什么
- AI该怎么帮你做

适合：学生做毕设、转行者做简历项目、个人开发者做MVP、小团队协作。

## 先看这里：你是哪种用户？

这套模板有**两种用法**，根据你的目标选一条走：

### 🎓 学生版：课程作业 / 毕设（快速跑通就行）

**目标：** 做出一个能跑的项目，交作业拿分。不用追求工业级标准。

**必须做的步骤：**
| 步骤 | 做什么 | 做到什么程度就行 |
|---|---|---|
| 0 | 调研 | 找2-3个竞品，列优缺点 |
| 1 | 需求分析 | 确定MVP做哪1件事 |
| 2 | 数据库设计 | 设计表结构，不用追索引/软删除 |
| 3 | 接口设计 | 设计5个左右接口 |
| 4 | 前端设计 | 设计3-4个页面 |
| 5 | 项目结构 | 建好目录，跑起来 |
| 6 | 项目记忆文件 | 生成AGENTS.md和MEMORY.md |
| 7 | 写代码跑通 | 本地能跑、能登录、能增删改查 |
| 8 | 代码审查 | 让AI帮你查一遍bug，改了就行 |
| 10 | 交付验收 | 对照需求走一遍核心路径，遗留严重问题清零 |

**可以跳过的步骤：**
- ❌ 第9步测试：不用追可数覆盖闸门、不用配CI。写3-5个核心接口的测试用例就行。
- ❌ 第12步部署：不用自己买服务器配Nginx。本地跑通就交作业；演示若走校园网/内网穿透，前端 5173 与后端 8000 两个端口都要能被访问者访问到（或前端走代理 / 同源部署）——只穿透前端端口，页面里的 `localhost:8000` 会解析到访问者自己的机器，后端必然连不上。

> 第10步交付验收不能跳过：哪怕学生版，也要对照需求把核心路径走一遍、确认遗留严重问题清零。

---

### 🚀 完整版：上线产品 / 简历项目（工业级标准）

**目标：** 做一个真的有人用的产品，或者写在简历上能经得起面试官问的项目。

**主线 0–10 一步不落；第11步增强按需做，第12步部署定稿后做：**
按模板里的工业级标准来——可数路径覆盖闸门、CI自动跑、验收对照需求逐项核对；验收通过后再视需要补第11步的一期内增强，功能定稿后进第12步部署（Nginx+HTTPS、数据库备份、回滚方案）。

## 怎么用这套模板

### 使用流程：一步一步走，走完一步发交接卡

1. **先打开第0步模板**，复制给AI → AI当教练引导你做调研
2. **走完第0步**，AI输出交接卡 → 你把交接卡复制下来
3. **打开第1步模板**，连同交接卡一起发给AI → AI接着带你做需求分析
4. **第1步选完技术栈**（比如FastAPI），从第2步开始：
   - 每发一步模板，都要把**对应的技术栈插件**一起发给AI
   - 一直带到第12步结束
5. **走到第6步**，AI帮你生成`AGENTS.md`——以后新开对话，直接把AGENTS.md发给AI就行，不用从头走
6. **走完第12步**，项目就完成了

> 💡 **为什么要每一步都带插件？**
> 第2步设计数据库要知道"金额用DECIMAL不用FLOAT"，第3步设计接口要知道"统一返回格式"，第8步审查要对照"反模式清单"——这些规则全在插件里。
> 只在写代码时才加载插件，前面设计的东西就会和后面生成的代码对不上。

## 多窗口协作：分工、材料与交接卡

> 单人一期默认不超过 3 个 AI 窗口；窗口多了会上下文割裂、口径漂移、共享盲区互相点头。（一手实证：MAST arXiv 2503.13657，MAS 相对单代理收益常很小；v3 p.26 Table 4 互验属战术层；p.25 定性：战术手段往往不一致、需结构策略。）

### 窗口数量（按风险分级）

- 底线 2 窗：A 执行 + B 复核；推荐 3 窗：再加 C 参谋。
- 触及安全 / 契约 / 数据 / 发布 → 3 窗；纯文案、格式打磨 → 可 1 窗。
- 1 窗 + 人复核必须登记人复核的失效模式（人没时间、没读、只看结论），不默认人一定会认真看。（自有经验值。）

### 三窗口身份

- **A 执行（开发）**：按基线 + 当前步模板落地写码 / 改文档 / 跑命令；先出方案再动手，改动留痕。禁自拍板范围选型、禁碰密钥、禁提前读后续步骤；不替复核下「没问题」结论，不替参谋做全局评审。
- **B 复核（独立质检 / 红队）**：基于事实造反例、找边界漏处、核测试覆盖，给可复现问题清单，独立下判断。持只读执行权：可跑测试、查库、读 git 历史、复现命令；仅 SELECT 与只读命令，禁 DML/DDL、禁跑 seed、禁清库，不改工作区文件。禁改码、禁替执行解释、禁被执行结论带跑；只给问题和依据，不指挥具体怎么改。
- **C 参谋（评审 / 总观）**：对范围、文档口径、外部规范查越界与不一致，提醒延后项，关键结论联网对照官方资料。禁钻单步实现、禁写码、禁替某窗做执行判断。

### 材料分配与交集

- **基线层三者共享**：附录A、需求文档、交接卡。
- **工作层按身份分读**：当前步模板仅 A；待改代码 A 读写、B 只读 diff、C 不钻；测试现状用例 A/B 读、C 不读；测试结果 / 命令输出 / 报错 A 产生、B 读、C 不读；接口 / 数据库 / 验收 / 测试报告 A 参考、B 不读、C 读。
- **交集规则**：A∩B 事实层重合（代码事实 / 测试证据 / 复现命令）；B∩C、A∩C 工作层不相交，仅基线层重合。交集只在事实层，结论层互不相交。
- **互斥项**：后续步骤模板、他窗结论、密钥三者互斥禁读。B 可读当前步模板与验收标准——标准与意图不互斥，互斥的只是他窗结论。
- **事实材料不得扣留**：扣留关键信息是高致命失败模式，几乎只出现在失败运行中；互斥的只能是结论，不能是事实。（一手实证：MAST v3 p.29 Table 7，ChatDev / MetaGPT 两框架样本。）

### 信息同步边界

- **可传事实层**：测试计数、覆盖率口径、代码 / 文档位置片段、命令输出与报错、现象（不带定性）。
- **先别传结论层**：通过 / 放行、选型倾向、归因解释、高置信主观结论。
- **验证顺序**：传事实 → 各自独立下结论 → 结论比对 → 不一致回事实层查。

### 文件标签与身份

- 身份由目录 / 文件名约定决定；文件头保留结构化字段（生成者 / 时点 / commit / 命令），手动填写。
- 读到非本身份材料，先声明「此文件非本身份可读，不作为判断依据」，不据此插手。

### 交接卡流向与字段

- **流向**：A→B；B→A 待改项、B→C 通过项；C→人收口；人 → 下一环节。
- **字段**：来源→去向；基线版本 + commit；事实材料（命令 + 分母口径 + 时点）；变更意图 / 设计理由；本窗口独立结论；移交事项；未决风险；证据三元组（命令 + 期望值 + 实得值 + 时点）。
- 其余步骤交接卡沿用第 8 / 10 步字段，本轮不逐张重写。

### 两条纠错原则

- **复核独立隔离**：复核方先不被作者结论带跑，独立看完代码与证据，再对照解释。
- **主动证伪**：先问「什么情况下不成立」，主动造反例推翻；只能做到「已知错误排除 + 关键路径有证据守住」，不能证明绝对正确。

### 依据分级

每条规则句末标注依据级别：**一手实证**（有可复算的一手研究 / 实测）/ **类比迁移**（从其他领域原则借用，非直接管辖）/ **自有经验值**（本项目经验，未跨样本验证）。本节的窗口身份、材料分配、交接卡字段与流程规则，除已句末标注一手实证 / 类比迁移的条目外，均为自有经验值。

> 人的最终判断与放行见附录A 第 9 条，本节不重复；复审往返上限与升级规则见第 10 步验收模板第 4 步，本节不重复次数。

## 怎么用？

第一次使用：
1. 复制 0调研模板.md 的全部内容
2. 粘贴给 AI（ChatGPT / Claude / 豆包都行）
3. 它会问你第一个问题，你回答就行
4. 它判断你答得对不对，不合格会让你重答
5. 走完调研，再复制 1需求分析教练 继续

整体流程：
1. 按顺序从 0 到 12，一步一步来
2. 每一步把对应模板复制给AI，让它像教练一样带你走
3. 写代码时，把附录A和项目记忆文件一起给AI
4. 做完一步，确认合格了再进下一步

## 设计理念：两类坑，两种覆盖方式

做项目踩的坑分两层，模板用不同机制分别覆盖，不要混为一谈：

### 第一类：普通边界问题（已知的未知）

**定义：** 你知道有这个场景存在，只是设计的时候忘了考虑它。

比如：用户上传空文件怎么办？知识库里没文件就提问怎么办？参数传空怎么办？这些场景你意识范围内有，只是漏了。

**覆盖方式：** 第1步需求分析、第2步数据库设计、第3步接口设计的模板里，都有强制的"异常点清单"，分业务类、技术类、用户类三类，设计阶段主动一个个确认，不许只做理想流程。

### 第二类：隐性暗坑（未知的未知）

**定义：** 你连这个东西存在都不知道，没人告诉你就会踩，更别说提前考虑了。

比如：中文 RAG 场景下 embedding 模型分中英文，默认英文模型检索会退化成关键词匹配；命令行程序不走 Windows 系统代理；换 embedding 模型必须重建向量库。你连"embedding 模型有语种之分"这个概念都没有，设计时根本想不起来要选模型。

**覆盖方式（两道防线）：**
1. **技术栈插件的常见坑清单**：把踩过的专家经验提前列在插件里，AI 设计和写代码时主动提醒。
2. **第7步开工前先扫坑**：模板里预先列的坑不可能覆盖全世界所有经验。第7步写代码之前，AI 必须主动搜索该技术栈 + 该场景的官方最佳实践和开发者踩坑记录，列成清单告诉用户，再动手写代码。

## 核心特点

- **全流程覆盖**：从调研到部署，不跳步
- **教练式引导**：不是给AI指令，是引导你想清楚
- **AI行为约束**：避免AI过度设计、硬编码、分层混乱
- **开工前主动扫坑**：写代码前先搜该技术栈和场景的最佳实践与常见暗坑，不靠人工列全所有经验
- **专业标准**：HTTP状态码规范、安全越权、测试分层、部署专业项
- **通用示例**：用products示例，不绑定具体项目
- **项目交接卡**：每步走完输出交接卡，跨会话不中断，不用从头再说一遍
- **多栈支持**：通用原则 + FastAPI/Django/Spring Boot示例，不是FastAPI专属
